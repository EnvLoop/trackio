# Cloud database pools

1. PostgreSQL cloud repositories own two pools: writes default to 10 connections and reads to 5. Both have zero overflow and a five-second checkout timeout. The private server TOML accepts `write_pool_size` and `read_pool_size`, each an integer from 5 through 1000. Changing these values requires restarting the service.
2. Existing server files remain valid. `WorkspaceStore` shares its repository's transaction and read-connection entry points; a Run, Job, Trial, writer, Workspace or Project does not create another pool. Capacity is per Repository and process, so replicas and rolling deployment overlap must be counted separately.
3. Repository `read_connection()` selects the read pool and starts a PostgreSQL READ ONLY transaction. Ordinary Engine transactions select the write pool. HTTP methods and paths do not participate in routing, and new endpoints reuse these data-access entry points. Workspace operations that update the Run fence use the write pool even when returning records or objects. Transactions retain one connection throughout; compiled SQL is not parsed or routed statement by statement.
4. HTTP requests do not reserve a pool slot for their entire lifetime. Actual connection checkout waits for the configured timeout; exhaustion returns a redacted `503 DATABASE_BUSY` with `Retry-After`. This does not discard buffered SDK events or acknowledge an uncommitted batch. Synchronous SQL and object operations run outside the HTTP event loop so a slow read cannot block all write handlers.
5. PostgreSQL application connections set statement timeout to 5000 ms and lock timeout to 1000 ms. Explicit initialization/migration uses a transaction-local 60000 ms statement budget, which resets at commit. These limits complement checkout timeout; increasing pool sizes does not remove lock contention. Administrative migrations require their own connection budget.
6. Workspace record reads reuse the transaction's connection. Object reads snapshot authorized metadata in one short transaction, release it before storage I/O, and recheck authorization, deletion and metadata before returning. Deletion, relocation or revocation during the transfer can reject the download; downloaded bytes are not returned after a failed final check.
7. Local SQLite retains its single Engine, pool size 3, file location and existing schema. The two PostgreSQL capacities do not split a SQLite file or create another local database. No schema migration is introduced by the pool change.
8. Event batches validate and encode before checkout, prefetch existing event identities in one query and insert new events in bulk. Existing batch/event content conflicts still reject atomically, and committed acknowledgments retain their meaning. This change does not add tenant fairness or refactor all upload and garbage-collection transactions. Unknown commit outcomes still require idempotent readback. Large capacities require database CPU, memory and lock-wait measurements as well as connection headroom.
9. With the accompanying JobMaster change, the default online ceiling is `30 × JobMaster processes + 15 × Trackio repositories`, plus administrative and other clients. A single process of each service therefore has a ceiling of 45; limits are not preallocated connections. Source changes do not release an image or deploy a service.
